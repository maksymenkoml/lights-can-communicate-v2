# NAS container profile

Issue: #9, stage 1 (offline preparation). Owner decisions (2026-11-20): the
first NAS release runs the core as one Container Manager compose project next
to the own Homebridge plugin (option C); Light Studio is served on the home LAN
without a password for now (#53); a later move to a plugin-managed core is #52.

## Why

The managed release renders launchd agents for the adapter and Light Studio and
a compose file for the bridge that publishes host ports. That shape cannot run
on the NAS:

- DSM holds TCP 80 and 443 on the NAS address; Hue clients accept no other
  ports, so the bridge needs its own LAN address.
- The Govee plugin on the NAS listens on UDP 4002 for Table Lamp; the adapter
  needs the same reply port, so it also needs its own LAN address.
- DSM has no launchd and its Python may be older than 3.10.
- A Linux host cannot reach its own macvlan containers, so the bridge cannot
  call the adapter through `host.docker.internal`, Homebridge cannot reach the
  core on its LAN address, and host-side checks of `127.0.0.1` see nothing.
- On macvlan the host can always bind UDP 2100. The Sync guard reads that as a
  lost port publication and would restart the bridge after every stall.
- Light Studio accepts only `127.0.0.1`/`localhost` Host headers.

## Goals

- An optional `container` section selects the profile. Without it, nothing
  changes for the Mac installation.
- `services` renders one `compose.json` with three services (gateway, adapter,
  studio) and no launchd agents. Docker supervises them.
- All three use the pinned diyHue image (multi-arch, Python 3.13), so DSM's
  Python is irrelevant.
- Components talk over a fixed internal bridge network; host-side commands
  (`ready`, installer stop checks) use the same addresses.
- Light Studio is reachable on the NAS address with an explicit list of
  accepted Host values; rebinding and cross-site protection stays.
- The Sync guard never restarts the bridge container in this profile.
- An owner live-output hold does not cause a restart loop under Docker.

## Non-goals

- No NAS access, deployment or migration; that is stages 2–5 of #9.
- No Light Studio password (#53) and no Homebridge custom UI (#5).
- No change of bridge identity handling: `gateway.mac` stays the identity
  value (#9 comment of 2026-11-20); the macvlan interface MAC is generated by
  Docker from the assigned address, which is unique on the LAN.

## Configuration

```json
"container": {
  "lan": {"parent": "eth0", "subnet": "192.168.10.0/24",
          "router": "192.168.10.1", "adapter_ip": "192.168.10.51"},
  "core_subnet": "172.30.250.0/29",
  "studio_hosts": ["192.168.10.5", "diskstation.local"]
}
```

- Requires the `gateway` section. `gateway.lan_ip` is the bridge macvlan
  address; `lan.adapter_ip` the adapter's. Both lie in `lan.subnet`, differ from
  each other and from `lan.router`. They must be outside the router's DHCP pool
  (owner check; not verifiable offline).
- `core_subnet` is private with a prefix of /29 or longer. Docker takes the
  first host address for the host side; the gateway, adapter and studio get the
  next three. Default `172.30.250.0/29`.
- `adapter.bind`, when given, must equal the adapter core address (the default
  in this profile). The adapter API is then not exposed on the LAN; Homebridge
  on the NAS host reaches it through the core network.
- `gateway.adapter_url` defaults to the adapter core address.
- `setup.bind`, when given, must be `0.0.0.0` (the default in this profile);
  the studio container has only the core network. `setup.port` is published on
  the NAS on the same port.
- `studio_hosts` lists the names or addresses a browser uses for the NAS;
  Light Studio accepts them with `setup.port` in the Host header, and loopback
  stays accepted. At least one entry.
- Every configured file must lie in the configuration directory or `state_dir`,
  the only mounted paths besides the release.

## Compose project

- Networks: `lan` (macvlan, `parent`, subnet and router) and `core` (bridge,
  `core_subnet`).
- `gateway`: existing entrypoint, environment and module mounts, no published
  ports or `extra_hosts`; static addresses on both networks.
- `adapter`: `python3 -I -B <current>/lights-can-communicate-v2.pyz adapter
  --config <config>`; static addresses on both networks.
- `studio`: the same archive with `setup`; core network only; publishes
  `setup.port`.
- All: `restart: unless-stopped`, `stop_grace_period: 20s`, the configuration
  directory read-only, `state_dir` read-write and the release read-only, each
  at its host path, so the configuration resolves identically on the host and
  in the containers. Paths go through `<base>/current`; Docker resolves it at
  creation, so activation requires a recreate (as for the Mac gateway today).

## Runtime changes

- `services.endpoints(config)` returns the adapter, studio and bridge URLs used
  by `ready`, the installer stop check and Light Studio. Without the profile
  they stay the loopback URLs of today.
- Light Studio gets the bridge URL from the profile, the accepted Host list and
  no gateway container (the guard then only restarts Sync; it never runs
  `docker`).
- With the profile, an active `live-output-hold` makes the adapter wait and
  re-check it instead of exiting 0, because `unless-stopped` restarts a
  finished container regardless of its exit code. SIGTERM still stops it.
- Installer start commands use `docker compose -f <current>/services/compose.json
  up -d --force-recreate`.

## Verification

Offline unit tests cover configuration rules, the rendered project, endpoint
selection, the Host list, hold waiting and the installer commands. CI renders
the project and validates it with `docker compose config`; the existing
isolated job already runs every contract inside the pinned image.
Network behavior (macvlan, discovery, host-to-core access, UDP 2100) is checked
in the NAS rehearsal (stage 3), not here.
